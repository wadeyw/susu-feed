### 1) Conceptual integrity and counting lines of code
- Track: ai_change / better_decisions
- Why it matters to me: This updates how I think about AI productivity itself. Simon Willison argues LOC *can* be a valid metric with coding agents — up to a hard limit. The limit isn't code output; it's cognitive capacity. A single engineer can churn out code 100× faster, but can't stay on top of 100× the codebase. Teams are still needed to load-balance cognition. More urgently, he surfaces the "Winchester Mystery House" problem: when adding features drops from a week to an hour, the old discipline enforced by time cost disappears. You keep building rooms because it's cheap, and conceptual integrity erodes.
- Tradeoff / tension: Speed of iteration vs. architectural coherence. The force that once kept software disciplined — the pain of building — is gone. What replaces it? Intentional constraint, not accidental friction.
- Implication: The scarce resource in AI-augmented development is no longer typing speed or even agent capability. It's the human capacity to hold the whole system in mind. This favors operators who can maintain conceptual integrity through process (design reviews, architecture gates, deliberate deletion) rather than hoping friction will save them.
- Action: When evaluating your own projects, ask: "What discipline replaces time cost now?" Build in deliberate stopping rules — not because building is hard, but because adding without subtracting is the new default pathology.

### 4) smolmachines / smolvm as a sandbox for untrusted code
- Track: own_business
- Why it matters to me: As agents become part of production systems, the question of "what can they run, and safely" stops being theoretical. Simon tested smolvm (Firecracker-based micro-VMs) for running untrusted Python and JavaScript with hardware isolation, no network, CPU/RAM limits, and guest-enforced timeouts. Cold starts: 0.6–1.5s. Warm execution: ~50ms. Everything worked as intended.
- Tradeoff / tension: Security vs. latency/cost. Shared-kernel containers (Docker) are fast but share the OS kernel — a vulnerability in one guest can escape to all. Hardware-isolated VMs (Firecracker, smolvm) solve the escape problem but add cold-start latency and memory overhead (~192–256MB per container with a full Chrome). For data transformation workloads, the question is whether 50ms warm execution is fast enough.
- Implication: If you're building any service that executes user-provided code or untrusted agent output, the sandbox choice matters. The smolvm approach is production-viable for batch/async work but may be too slow for interactive agent loops. The 50ms warm execution number is useful benchmarks context.
- Action: If you're evaluating sandboxing for agent-mediated services, this is a concrete data point. The GitHub Actions test approach (Simon's agent hit the KVM limitation in its own container and pivoted to GitHub Actions runners) is itself a pattern worth noting: test your infrastructure assumptions in an environment that actually has the hardware you need.
- Confidence: medium
- Source: Simon Willison — https://simonwillison.net/2026/Aug/19/smolmachines-untrusted-sandbox/
