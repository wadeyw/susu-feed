### 2) When str.lower() is a Security Vulnerability in Python
- Track: better_decisions
- Why it matters to me: Seth Larson (PSF Security Developer-in-Residence) found CVE-2026-17084: Python's `str.lower()` uses the current Unicode version (17.0.0) instead of Unicode 3.2.0, which the StringPrep/IDNA 2003 RFC explicitly requires. A single function call produces different results depending on the interpreter's Unicode version, breaking spec compliance silently. The fix required mapping every Unicode codepoint to detect behavioral drift. This is a masterclass in where real risk hides — not in dramatic exploits, but in the mundane assumptions built into everyday functions.
- Tradeoff / tension: Updating a language's Unicode data improves general correctness but can silently break code that depended on spec-stable behavior. The tension between "be current" and "be spec-compliant" is a pattern that repeats across infrastructure decisions.
- Implication: For decision hygiene — the most dangerous vulnerabilities are the ones that look correct but produce wrong results under specific conditions. When building or evaluating systems, ask: where does this depend on an implicit version, locale, or environment assumption? The risk is never in the obvious code path; it's in the edge case that passes review because it "looks fine."

- Track: own_business

EVE has been running on Stackless Python since 2003, with its last major upgrade 16 years ago.
- Tradeoff / tension: Stay on Python 2 (known, stable, but dying — no security updates, no ecosystem support) vs. migrate now (massive engineering investment, risk of silent behavioral bugs like the division change) vs. migrate later (more code rot, harder migration, talent increasingly unavailable). This is the technical debt trilemma: you can delay the cost, but you can't avoid it.
- Implication: For business builders, this is a warning about the compounding cost of "we'll upgrade later." Every year of delay on a critical platform decision multiplies the migration cost. The 20,000 manual-review spots aren't just lines of code — they're decisions that need human judgment because automated tools can't resolve semantic differences. The lesson: architecture decisions that seem benign today (which language version, which framework) become existential risks in 10-15 years. Make the hard decisions early, not when the alternative is a 2.4M-line emergency migration.

## Idea sparks

- The C2PA failure mode suggests a broader pattern: verification infrastructure that assumes perfect upstream data is fragile. Any system built on "trust but verify" needs to first ask "can the trust layer be gamed at the source?" This applies beyond media — think supply chain provenance, academic credentials, professional certifications.
- The Python str.lower() vulnerability is a concrete example of "spec drift" — when an implementation slowly diverges from its specification without anyone noticing. This pattern appears in databases, protocols, and APIs. Building a habit of checking "what version am I actually running against?" could catch more issues than any security scan.
- EVE's migration reveals a practical rule: if your codebase has a behavioral difference between versions (like integer division), you should be able to enumerate those differences before you migrate. The 20,000 manual-review spots exist because the difference wasn't documented — it was discovered during migration. Documenting behavioral diffs in your own projects could reduce future migration cost dramatically.
